2.7.5 Aggregation (Continued)

Consider a database that models employees who work on jobs at branches, and managers who manage those tasks. Figure 2.18 shows an E-R diagram with two quaternary/ternary-style connections: works-on (relating employee, job, and branch) and manages (relating employee, job, branch, and manager).

Figure 2.18 contains redundant data. Every $(e, b, j)$ combination in manages is also present in works-on: $$\pi_{employee, branch, job}(\text{manages}) \subseteq \text{works-on}.$$

Why Not Make manager a Multivalued Attribute?

If manager were a simple value instead of an entity, we could make manager a multivalued attribute of the relationship works-on. However, that design makes it more difficult (both logically and in query execution cost) to find all $(\text{employee}, \text{branch}, \text{job})$ triples for which a manager is responsible. Because manager is an entity set, this alternative is ruled out.

Definition (Aggregation): Aggregation is an abstraction through which relationships are treated as higher-level entities.

To model the example cleanly, treat the relationship set works-on (which relates employee, branch, and job) as a higher-level entity set named works-on. Treat this higher-level entity set in the same way as any other entity set. Then create a binary relationship manages between works-on and manager to show who manages what tasks. Figure 2.19 shows this notation.

2.7.6 Alternative E-R Notations

There is no universal standard for E-R diagram notation. Different textbooks and E-R diagram tools use different symbols. Figure 2.20 summarizes the complete set of E-R symbols used in this chapter, and Figure 2.21 shows widely used alternative notations:

  • Box-style entity sets: An entity set can be drawn as a rectangle with the entity name placed outside above the box, and the attributes listed vertically inside the box. Primary key attributes appear at the top, separated from non-key attributes by a horizontal line.
  • Edge labels * and 1: Cardinality constraints can use * (many) and 1 (one) on edges out of a relationship diamond to depict many-to-many ($M:N$), one-to-one ($1:1$), and many-to-one ($N:1$) relationships. (The one-to-many case is symmetric to many-to-one.)
  • Diamondless “crow’s foot” notation: Relationship sets are drawn as lines between entity boxes without diamonds. This notation models binary relationships only. A forked “crow’s foot” at an entity box indicates the “many” side.

2.8 Design of an E-R Database Schema

The E-R data model gives a database designer flexibility when modeling an enterprise. The designer must make six key structural decisions based on a thorough understanding of the enterprise:

  1. Attribute vs. Entity Set: Decide whether to use an attribute or an entity set to represent an object (Section 2.2.1).
  2. Entity Set vs. Relationship Set: Decide whether a real-world concept is expressed more accurately by an entity set or by a relationship set (Section 2.2.2).
  3. Ternary vs. Binary Pair: Decide whether to use a ternary relationship or a pair of binary relationships (Section 2.2.3).
  4. Strong vs. Weak Entity Set: Decide whether to use a strong or a weak entity set (Section 2.6). Because weak entities are existence dependent on a strong entity, a strong entity set and its dependent weak entity sets can be treated as a single “object” in the database.
  5. Generalization (ISA Hierarchy): Decide whether generalization is appropriate (Section 2.7.2). A hierarchy of ISA relationships improves modularity because common attributes of similar entity sets appear in one place.
  6. Aggregation: Decide whether aggregation is appropriate (Section 2.7.5). Aggregation groups part of an E-R diagram into a single entity set so it can be treated as one unit without concern for its internal structure.

2.8.1 Design Phases

A high-level data model provides a systematic conceptual framework to specify user data needs and database structure. Database design proceeds through four phases:

  1. Specification of User Requirements: Interact extensively with domain experts and prospective users to characterize all data needs. Output: a specification of user requirements.
  2. Conceptual-Design Phase: Choose a data model (here, the E-R model) and translate user requirements into a conceptual schema. In the E-R model, the schema specifies all entity sets, relationship sets, attributes, and mapping constraints.
    • Review the schema to verify that all data requirements are satisfied with no conflicts, and remove redundant features. Focus on data and relationships, not physical storage details.
    • Include a specification of functional requirements: users describe the operations (transactions) performed on the data, such as modifying/updating data, searching/retrieving specific data, and deleting data. Review the schema against these functional requirements.
  3. Logical-Design Phase: Map the high-level conceptual schema onto the implementation data model of the target database system.
  4. Physical-Design Phase: Specify the physical features of the database, including file organization and internal storage structures (covered in Chapter 11; full database design treatment in Chapter 7).

2.8.2 Database Design for Banking Enterprise

This section applies the first two design phases to a realistic banking enterprise. (Only selected banking aspects are modeled to keep the example clear.)

2.8.2.1 Data Requirements

Based on user interviews and enterprise analysis, the banking enterprise has these requirements:

  • Branches: The bank is organized into branches. Each branch is located in a specific city and is identified by a unique name. The bank monitors the assets of each branch.
  • Customers: Customers are identified by customer-id values. The bank stores each customer’s name, street, and city. Customers can hold accounts and take out loans. A customer can be associated with a particular banker (loan officer or personal banker).
  • Employees: Employees are identified by employee-id values. The bank stores each employee’s name, telephone number, the names of the employee’s dependents, the employee-id of the employee’s manager, and the employee’s start date (used to calculate length of employment).
  • Accounts: The bank offers two account types: savings and checking. Accounts can be held by more than one customer, and a customer can hold more than one account. Each account has a unique account number, a balance, and a record of the most recent date each customer accessed the account. Each savings account has an interest rate; each checking account records overdrafts.
  • Loans: A loan originates at a particular branch and can be held by one or more customers. A unique loan number identifies each loan. The bank tracks the loan amount and loan payments. A payment number does not uniquely identify a payment across all bank loans, but it does identify a particular payment for a specific loan. Each payment records a date and an amount.
Scope Note on Deposits & Withdrawals

A real bank also tracks deposits and withdrawals on savings and checking accounts just as it tracks loan payments. Because the modeling pattern is identical, deposits and withdrawals are omitted here to keep the example compact.

2.8.2.2 Entity Sets Designation

From the requirements in Section 2.8.2.1, we designate the initial entity sets and attributes:

  • branch: branch-name, branch-city, assets.
  • customer: customer-id, customer-name, customer-street, customer-city (and possibly banker-name).
  • employee: employee-id, employee-name, telephone-number, salary, manager; plus multivalued attribute dependent-name, base attribute start-date, and derived attribute employment-length.
  • Account entity sets: savings-account and checking-account. Common attributes: account-number and balance (factored into superclass account). Additional specific attributes: interest-rate on savings-account; overdraft-amount on checking-account.
  • loan: loan-number, amount, originating-branch.
  • Weak entity set loan-payment (labeled payment in Figure 2.22): payment-number, payment-date, payment-amount.

2.9 Reduction of an E-R Schema to Tables

We can represent a database that conforms to an E-R schema by a collection of relational tables. For each entity set $E$ and each relationship set $R$ in the database, there is a unique table assigned the name of that entity set or relationship set. Each table has multiple columns, and each column has a unique name: $$T_E(A_1, A_2, \dots, A_n) \quad \text{and} \quad T_R(K_1, K_2, \dots, K_m, B_1, \dots, B_p).$$

Both the E-R model and the relational database model are abstract, logical representations of real-world enterprises. Because the two models use similar design principles, we convert an E-R diagram into a table format to obtain a relational database design from an E-R schema.
